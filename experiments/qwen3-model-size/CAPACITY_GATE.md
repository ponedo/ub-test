# Qwen3-30B-A3B initial capacity gate

Status: initial gate blocked on existing software limits. The user subsequently approved generic configurable ceilings; see `CAPACITY_DESIGN.md`. This document retains the original failure evidence.
At the initial gate no implementation was changed. The subsequent patch changes application capacity checks only; native protocol, planner, network and compute remain unchanged.

Official pinned dimensions and sources are in `MODEL_PARAMETERS.md`, `config.json` and `provenance.json`.
The new `fixed-config.json` preserves EP64, 128 experts, top-k 8, Zipf 1.1, routing seed 20261016, main placement, planner parameters, 100 Gbit/s links, 20 ns link delay, 1024-byte TA, 4096-byte weight chunks, and compute assumptions. Only H/I change to 2048/768.

## Actual execution

A fresh accepted-native build ran No Balancing at 256 tokens:
- 2048 assignments, 4046 remote WQEs, 16184 TAs.
- Layer latency 7.957270688 ms.
- Simulator wall time about 2.51 s, peak RSS 144004 KiB.
- Online per-task/segment/payload checks and independent pre/postflight PASS.
- Summary mode; no raw protocol trace generated.

Exact measured timing/resource and validation evidence is in `evidence/`.

The same original synthetic routing produces **51 replicas** in the accepted planner. The real adapter rejected UltraEP with `payload safety bound`. At that initial gate neither Direct nor Chunk Streaming had run at Qwen size. Subsequent approved runs are reported separately in REPORT.md and results/.

## Original limits and historical proposal

1. Adapter `direct-weight-forward/adapter.py` and executor `pair-jetty/pair-layer.cc` both require:
   `2 * assignments * hidden * dtype_bytes + replicas * expert_weight_bytes <= 256 MiB`.
   Here this is `16 MiB + 51 * 9 MiB = 475 MiB`. This is a logical payload budget, not a measured RSS or OOM. It excludes object, protocol, duplicated buffer and verifier overhead.
2. Executor additionally requires at most 20000 weight graph edges. Preserving the existing relay grouping and 4096-byte chunks gives 62232 weight WQEs, independently generated by the unchanged native graph tool (27 relayed replicas * 2304 chunks + 24 direct fallbacks), exceeding that second independent cap. The graph-tool result is not a completed network experiment.

The original proposal, before approval, was: retain current defaults, add bounded explicit payload/task budget options with checked arithmetic and consistent adapter/executor/preflight validation; authorize a 256-token trial only using budgets sufficient for 475 MiB and 62232 edges. Preserve the 300 s wall, 6 GiB process-tree RSS, 7 GiB address space and free-disk/memory guards. Do not change chunk size, assignment routing, number of WQEs, segmentation or ACK window.

Validate default-limit rejection and boundary arithmetic first, old small-model exact timing/counter/payload parity next, then Direct followed by Chunk. Report measured resources before any larger sweep. The existing graph adapter builds dependency lists by scanning weight transfers, so host preparation cost may be significant at 62232 edges; no optimization has been silently introduced.

## Compute assumptions

Three bias-free expert matrices yield 4,718,592 parameters, 9,437,184 BF16 bytes, and GEMM-only 9,437,184 FLOPs per assignment. Both Dispatch and Combine carry 4096 bytes per assignment; no packing. Compute remains the existing 1000 peak GFLOP/s * 0.5 utilization = 500 effective GFLOP/s assumption, with integer-picosecond rounding and 100 ns setup per nonempty physical expert. Thus GEMM service is 18874.368 ns per assignment plus setup. SiLU, elementwise multiplication, router operations, HBM bandwidth/cache, GEMM efficiency scaling and real Ascend measurements are not modeled. Planning 200 ns and reroute 100 ns are fixed assumptions, not host planner timings or size-calibrated hardware costs.

Regression harness setup notes: an initial invocation supplied a summary-default executable to the historical pre-logging `old-binary` slot, so the offline oracle could not find events.csv. A second invocation rejected an invalid case alias before execution. Both setup logs remain locally preserved; the final run uses the required original pre-logging executable and valid fixture names. No executor or test assertions were changed.

Final small-model regression: all four fixtures (No Balancing, Direct, Chunk Streaming, multi-chunk/multi-TA pipeline) passed summary/events/debug and old full-debug comparison, including original strict offline verification. Parameter tests PASS; the 256-token routing CSV SHA256 exactly equals the prior accepted EP64 routing.
