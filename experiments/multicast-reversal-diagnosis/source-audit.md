# Native source audit for multicast reversal diagnosis

## Scope and provenance

This is a source-mechanism audit, not a measured root-cause verdict. It adds no protocol, topology, scheduling, queue, congestion-control, or performance changes. All line references below refer to the private `diagnosis-native` checkout and the diagnostic experiment sources, inspected on 2026-10-21. Native paths are relative to `diagnosis-native/src/unified-bus/model/`; application paths are relative to `diagnosis-work/experiments/multicast-reversal-diagnosis/` unless stated otherwise.

The native implementation files `ub-switch-allocator.cc`, `ub-port.cc`, `ub-ingress-queue.cc`, `ub-switch.cc`, and `protocol/ub-transport.cc` were individually SHA-256 checked against `diagnosis-private/real-3136-v2/ledger.json` → `identities.source-identity`; all five matched before the v3 observer-only additions below. `ub-switch-allocator.cc` then gained the two explicit callback-outcome observations; its v3 hash must come from the regenerated manifest and v3 run ledger. That v2 ledger records both formal strategies and 3136 Gbps. This establishes which native source was executed, not that every diagnostic interpretation is valid: observer corrections and the independent analyzer remain the authority for final measurements. The accepted-versus-diagnostic file manifest is `native-diagnostic-manifest.json`.

## Configuration actually inherited

- **3136 Gbps:** the accepted input `bandwidth-private/real-3136/{chunk-streaming,multicast-v2}/config.json` has `runtime.link_gbps = parameters.link_gbps = 3136`. `prepare.py:9-11` copies and verifies these inputs without changing the rate. `layer.cc:233-240`, `Layer::Init`, sets every `UbPort` data rate to `linkGbps * 10^9` bits/s. This is not a 3136 GB/s setting.
- **CC disabled already in the accepted experiment:** diagnostic `layer.cc:287` binds `UB_CC_ENABLED` to false before topology setup. The same binding exists in the accepted `bandwidth-work/experiments/qwen-roofline-compute/layer.cc:284` and its integration ancestor at `bandwidth-work/experiments/ultraep-multicast-integration/layer.cc:275`. It was not disabled by this diagnostic patch to improve performance. Consequently this case does not test active native CC/CNP throttling. This does not mean the native implementation lacks CC support.
- **CBFC remains enabled:** `ub-switch.cc:61-74` defaults `FlowControl` to `FcType::CBFC`; `Layer::Init` does not override it. Application `layer.cc:340` reads actual credit state through `UbCbfc`, and `pair-multicast-v2.h:97` explicitly requires that cast and finite credit/egress capacity to pass. CBFC and transport CC are separate mechanisms: disabling the latter does not remove link-credit constraints.
- **Native RR, 5 ns allocation service:** `ub-switch.cc:75-80` defaults the VL scheduler to SP; `UbSwitch::InitAllocator` at `ub-switch.cc:211-225` maps SP to `UbRoundRobinAllocator`. `ub-switch-allocator.cc:110-114` defines `AllocationTime = NanoSeconds(5)`. The application does not override that attribute, and `pair-multicast-v2.h:57` requires a native RR allocator. Thus “RR” here means RR ingress selection within the existing priority traversal, not global fairness across every VL.

## Executed scheduling and buffering path

1. `UbSwitchAllocator::TriggerAllocator`, `ub-switch-allocator.cc:355-385`, coalesces repeated wakes while an output allocator is running, records `m_runAgain`, and selects an ingress queue before scheduling completion. It does not allocate a new packet immediately at every wake. Once it reaches selection, it calls `ScheduleAllocation` even when `PickNextIngressQueue` returned null: a scheduled allocation callback can consume its delay and produce no packet without any stale-grant rejection.
2. `ScheduleAllocation`, `ub-switch-allocator.cc:188-218`, schedules the existing completion callback after `m_allocationTime`. The diagnostic `GrantStart` observes that service interval; it adds no event.
3. `FindNextEligibleIngressQueue`, `ub-switch-allocator.cc:507` onward, uses the already-existing `IsEmpty`, `IsLimited`, and flow-control eligibility checks. `UbRoundRobinAllocator::SelectNextIngressQueue`, `:842-892`, traverses priorities, selects the next eligible ingress slot, and advances that priority's RR cursor.
4. `UbRoundRobinAllocator::AllocateNextPacket`, `ub-switch-allocator.cc:708-835`, consumes the selected grant. The preexisting adapter-specific `RevalidateOnCommit` path at `:729-749` rechecks coordinated pair heads; a rejected selection pays a new ordinary allocation interval. Ordinary native queues without that attribute keep their existing grant semantics. The capacity check happens before `GetNextPacket`; an egress-full rejection leaves the packet at ingress. Diagnostic `GrantCommit` observes a successful existing egress enqueue, after its existing flow-control callback. V3 appends `GrantRejected` inside the existing compound revalidation rejection branch (`:737-744`) and `GrantNoIngress` in the existing no-selected-queue alternative (`:812-818`). Neither repeats or splits the original short-circuit predicates. Both carry node/port/queue/time only; duration comes from matching the preceding per-port `GrantStart`, not a hardcoded 5 ns. These outcomes distinguish a rejected old selection from a callback that had no ingress queue. `starts - commits` alone is not a stale-rejection count.
5. `UbSwitch::GetOrCreateVoq`, `ub-switch.cc:397-438`, creates/registers a queue for output, priority, and input. `UbPacketQueue::Push` and `Pop`, `ub-ingress-queue.cc:148-211`, maintain FIFO packet storage. Physical VOQ residence is the matched push-to-pop interval for each FIFO enqueue occurrence in the same queue. Packet UID alone is not unique across copies and serves only as a consistency check. The old `m_headArrivalTime` is reset when a new head appears and is not the original enqueue timestamp of every waiting packet.
6. `UbPort::EnqueueToEgress`, `ub-port.cc:94-134`, and `UbEgressQueue::DoEnqueue/DoDequeue`, `:61-86` / `:136` onward, represent the finite egress queue separately from VOQ. `UbPort::DequeuePacket`, `:552` onward, sets the send state BUSY and removes the packet from egress. An allocation completion is not the same boundary as physical transmission.
7. `UbPort::TriggerTransmit`, `ub-port.cc:1068-1105`, can prefetch allocation while the port is busy and egress is empty. This allows some 5 ns allocation service to overlap serialization. `NotifyAllocationFinish`, `:1108` onward, cannot start a second send while busy.
8. `UbPort::TransmitPacket`, `ub-port.cc:829-903`, computes serialization from actual packet size and data rate, then separately adds explicit delay, interframe gap, and NOB occupancy as applicable. The successful `TxStart` observation distinguishes serialized transmission from total busy occupancy. `TransmitComplete`, `:526-550`, ends BUSY and triggers subsequent work. `Receive`, `:944` onward, is the actual receive callback, not a TX-time estimate of arrival.

## Source TP window and response priority

- `UbTransportChannel::GetNextPacket`, `protocol/ub-transport.cc:881-940`, tries the existing CNP queue, then ACK queue, then enabled retransmission work, before new data. ACK/CNP bypass in `IsLimited` (`:3042` onward) means queued control work is eligible; it is not evidence that the next new-data packet is permitted.
- `IsInflightLimited`, `protocol/ub-transport.cc:2863-2869`, compares `m_psnSndNxt - m_psnSndUna` with `m_maxInflightPacketSize`. Despite the stale adjacent comment, `IsLimited` actually calls this function. The difference is sequence-space outstanding packets, not physical wire bytes, not WQE queue depth, and not an RTT measurement.
- `AdvanceNewDataSendState`, `protocol/ub-transport.cc:789` onward, advances `m_psnSndNxt` when the TP generates its new packet. This precedes source-port wire completion. `AdvanceSenderAckFromPlainTpack`, `:1764-1790`, unwraps ACK PSN within the current sender window and advances `m_psnSndUna` only for real progress.
- `RecvTpAck`, `protocol/ub-transport.cc:1924` onward, handles CNP, NAK, and ACK/SACK paths. `FinalizeTransportAckProgress`, `:1865` onward, and `UpdateSenderAfterTransportAck`, `:1841-1863`, update completion/continuation and may wake transport transmission. `EnqueueTransportResponse`, `:2270` onward, is actual receiver response queue admission.
- The observer does not add an `IsLimited`, CC, retransmission, or dequeue call. It reports values after existing branch decisions. The saved `m_sendWindowLimited` flag can persist and must not be treated as a fresh predicate result. `TpEmpty` is a separate observation of the existing emptiness result.
- `TpAckBefore` is at transport ACK entry, after the outer DL/network/IP/UDP layers have already been stripped by dispatch; `TpAckAfter` may have no parseable protocol bytes left. Correlate these events with earlier packet identity, not a fresh assumption that every pointer still contains a full wire frame. `TpResponseBefore/After` brackets `RecvDataPacket` (`:2531` onward), which includes ordinary request data as well as TA response traffic.

## Empty TP versus outstanding packets and admission capacity

`HasPendingTransmitWork`, `protocol/ub-transport.cc:3022-3040`, first checks CNP, ACK, and enabled retransmission work. With none, it returns false if the segment vector is empty, or if `sndNxt >= tpPsnCnt`: there is no remaining **admitted unsent** packet work. It does not require `sndNxt == sndUna`. Therefore an Empty observation can coexist with hundreds of outstanding unacknowledged packets.

Admission has distinct gates. `CanContinueAcceptedWqeSegment` (`protocol/ub-transport.cc:2712-2715`) requires both retained-SQ capacity and active-send capacity. `kShallowPipelineActiveSendDepth = 2` (`:40`), `GetActiveSendSegmentCount` (`:2826-2836`), and `CanScheduleAnotherSegment` (`:2848-2851`) cap unsent active segments; sent-complete segments do not count against that active depth. `IsWqeSegmentLimited` (`:2854-2860`) instead tests the full retained segment vector size against `m_maxQueueSize`; `DefaultMaxWqeSegNum` defaults to 1000 (`:260-264`). These are segment-admission limits, separate from the outstanding-packet PSN window.

After a segment finishes sending, `AdvanceNewDataSendState` (`:811-812`) can retry TA continuation. `CompleteAckedWqeSegments` (`:1806-1838`) erases acknowledged segments and can retry again. `UbTransportChannel::TryContinueJettyTransmission` (`:2917-2935`) delegates to `UbTransaction::TryContinueJettyTransmission(Ptr<UbTransportChannel>)`, `protocol/ub-transaction.cc:865-891`, which rechecks both capacity gates before continuing transport and jetty queues. The jetty-number overload at `ub-transaction.cc:823-862` separately checks jetty limiting, dispatch readiness, pending TP cleanup, remaining bytes, and send/order eligibility.

For example, a reported snapshot with `sndNxt=18364`, `sndUna=17853` has 511 outstanding sequence positions. If its packet-window cap is 1000, it is below that one cap at that instant. This neither proves zero ACK dependence nor excludes segment admission, upstream TA/jetty eligibility, or grouped-member coordination as explanations of an Empty period. The snapshot alone does not identify which gate prevented the next admission. Attribution requires the recorded timeline and independent analyzer; missing `IsLimited(Inflight)` hits are not proof that all transport-window or admission mechanisms were irrelevant.

## Envelope and native branch boundaries

`UbSwitch::HandleWriteV2`, `ub-switch.cc:2240-2312`, decodes the serialized envelope, reconstructs native branches from envelope headers and shared payload, resolves routes, and admits processing. `CompleteNetworkProcessing`, `ub-switch.cc:2122` onward, makes those branches visible in the existing output VOQs. An envelope UID is not a branch UID. The diagnostic mapping records parent UID, operation/group, sequence, and branch index without adding packet tags or changing payloads. Source envelope counts and downstream branch counts therefore cannot be substituted for one another in service-demand or wire-byte calculations.

The existing pair adapter's `AllReady` / `Limited` / `Pull` at `pair-multicast-v2.h:68-92` coordinates member TP heads. A jointly ready envelope can be withheld by one member's queue/window/control state even when the shared source link could otherwise serialize bytes. These checks are part of the accepted adapter, not new diagnostics.

## Why equal 5 ns grants do not imply equal resource waiting

The constant allocation interval is only one service component. Two strategies can have the same service time per successful grant yet different:

- numbers and timing of source envelopes versus downstream native packet grants;
- ingress competition, RR positions, and VL/control-work precedence;
- time a coordinated member head is not eligible, including TP-window dependence on ACK progress;
- finite-credit and egress-capacity blocking;
- burst alignment and FIFO residence at each physical output;
- overlap of allocation with a busy port versus exposed idle bubbles;
- wire packet sizes and hence serialization occupancy at the same bit rate.

These are mechanisms supported by source, not findings that any one mechanism dominates this reversal. Do not infer the measured cause from aggregate packet savings alone, multiply every grant by 5 ns as if all allocation were exposed on the critical path, or add overlapping wait/service intervals into a latency sum. Final attribution must use validated diagnostic cohorts, explicit source/port filters and coverage, matched native identities, critical-path/tail evidence, and the independent analyzer output. Unclassified or excluded intervals remain visible rather than being assigned a convenient cause.
