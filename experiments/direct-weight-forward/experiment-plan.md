# Phase 1 Direct weights + prefill Forward — preregistered experiment group

Base a9ba52f; fixed UltraEP 94cab099. User explicitly authorized development, execution and independent branch push. Implementation lives in ub-test; generated C++ scenario is copied into ns-3-ub/scratch. This custom stateful Transaction executor reuses the accepted PoC/NoBalancing path, not a static traffic.csv workflow; no protocol-stack changes are planned.

Claim: the accepted plan can be realized through real Direct weight WRITE transactions and an end-to-end single-layer prefill schedule while preserving all routing/byte/dependency invariants. Control is NoBalancing in the SAME new executor. Treatment is upstream-compatible Planner + planning/reroute latency + Direct weight distribution. Fixed controls within each pair: identical logical routing trace, main placement, network, per-assignment WQE rule, token bytes, compute formula/throughput/setup, TA segmentation and observability. Only policy and its necessary overheads change.

Dependency evidence: paper v3 Figure 8 / §4.2 explicitly permits weight sync overlapping reroute, but dispatch waits for weight sync to finish. Therefore dispatch gate = planning_end + max(reroute duration, observed target-ready weight duration). Every NPU batch additionally requires all its dispatch assignments and all nonempty physical weights; experts serialize on that NPU, NPU batches may overlap; combine waits for its NPU batch. Layer begins with already available post-gating routing information (notify/gating excluded equally).

Prediction before execution: balanced/no-replica cases cannot benefit from planner overhead. Hot cases reduce compute imbalance but Direct weights can outweigh it, especially for small batches; no guaranteed speedup. Falsification: any wrong byte, missing/duplicate assignment or weight, quota mismatch, early dispatch/compute/combine, deadlock, nonidentical pair controls, or speedup using a non-layer metric. A speedup below 1 is a valid result, not a failed run.

Synthetic scaled SwiGLU model: H=64, I=128, dtype=2 bytes, three dense matrices => 6*H*I FLOPs per assignment, excluding elementwise activation/gating cost; exact unquantized weights=3*H*I*dtype=49152 bytes per replica. This is a scaled functional model, not a named production MoE or real NPU speed claim. Peak=1000 GFLOP/s, utilization=500/1000, setup=100 ns/expert batch, planning=200 ns, reroute=100 ns, UB links=100 Gb/s, propagation=20 ns, TA segment=1024 bytes are explicit synthetic assumptions. A two-matrix case keeps legacy functionality. Segment/timing edge cases are fixed in matrix before runs. No hardware-public parameter claim is made.

Topology: N endpoints, one N-port switch, one full-duplex link each, explicit unique shortest routes and required pair TPs; same accepted network construction. Both directions use true WRITE/Transaction packets. Trace enables task/packet/port/all-packet artifacts as in the prior baseline. Config source keys are the existing executable's resolved UbPort::UbDataRate / UbLink::Delay and UB_* trace/CC globals; no guessed new keys.

Checkpoint policy: continue_full_matrix for prediction mismatches; stop immediately for correctness failure. Serial builds/runs. Stages: adapter canary -> Direct weight/ready canary -> small forward -> fixed EP64 -> repeatability and old regressions. No user pause is needed on successful checkpoints. Cases/commands are generated from frozen cases.py and matrix.yaml before suite execution; ledger records running/success/failure. Re-running overwrites only this new experiment's evidence (config+seed deterministic); prior modules and evidence are untouched.

Artifacts: input/config/Planner plan; assignment and transfer tables; raw event stream including all target byte-verification and completion events; native ns3 traces; exact command/return code; independently reconstructed summary; pair latency/speedup/timeline report. Payloads are synthetic deterministic bytes with expert/main provenance, checked byte by byte; no numerical MLP is claimed. Compute is a timed resource model. Separate numerical model and CPU planner wall time never become simulated planning latency.
