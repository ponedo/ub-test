# Multicast v2 高带宽瓶颈受控消融

基线：`b149fdd4d40d72791a84b788443b0450c41f6180`。固定 Qwen3 L37 / 2048 Tokens / EP64 / 3136 Gbps / Roofline。只改变 Jetty TA Window；原生 TP Packet Window、Planner、真实输入、协议、拓扑及 5 ns 仲裁服务保持不变。

## 结论

**扩大 Jetty 窗口有小幅收益，但没有消除 Multicast 相对 Chunk 的性能反转。** 下表均为 ns-3 模拟时间，不是宿主机运行时间，也不是硬件测量。

| Jetty TA Window | Chunk Weight (μs) | Multicast Weight (μs) | Chunk Layer (μs) | Multicast Layer (μs) |
| ---: | ---: | ---: | ---: | ---: |
| 512，原始基线 | 552.893591 | 717.182855 | 732.284971 | 898.435170 |
| 1024，容量消融 | 552.893591 | 698.240735 | 732.284971 | 895.291479 |
| 2048，容量消融 | 552.893591 | 688.812836 | 732.284971 | 886.365447 |

- 2048 相对 Multicast 自身 512 基线：Weight 降低 **3.955758%**，Layer 降低 **1.343416%**。它仍比同窗口 Chunk 的 Weight 慢 **135.919245 μs**。
- 实验 A 按停止条件标记 **UNSUPPORTED**：最小无效回调抑制改变了共享端口的跨 TP 仲裁顺序，无法满足本轮语义保持要求。未运行 A 的正式性能实验，未伪造加速结果，也未混合 A+B。这不证明所有调度优化都不可能。
- 原始 512 场景存在可审计的反馈服务下界：四成员的最后 TA 提交至少要求 **143,360** 个反馈报文经过返回源 NPU 3 的交换机出口；原始串行 5 ns 仲裁需要至少 **716.8 μs**，实测 Weight 为 717.182855 μs。这是有条件的模型约束，不是对 164.289264 μs 差距的独立因果百分比分解，也不是可直接回收的时延。
- 扩窗后，Weight Ready 提前不等于原生事务排空提前。未完成反馈与后续阶段的重叠变化，解释了为何不能把 Weight 收益直接当成 Layer 收益；2048 下 NPU 3 的计算批次启动可以早于最后选定权重 TAACK，排空不是该批次启动的通用门槛。
- 1024→2048 仍有进一步收益，实际 Jetty 占用达到 2048，排除了“硬性 1000 TA 上限导致完全平台”的简单假设。原生 1000 个保留分段/PSN 容量是另一层状态，不能混为一谈。
- 出口 59 的前向 Weight VOQ 驻留增加，而 Weight 完成仍改善。返回出口 3 的反馈排队及持续服务是重要约束；各机制的唯一中介贡献没有被完全隔离，不把排队时间、AllReady 检查次数或重叠窗口暴露直接相加。

**建模边界：** 3136 Gbps 在这里是一个逻辑聚合端口，仍保留单端口每包 5 ns 的仲裁服务。结论不能表述为 CloudMatrix384 实机吞吐或组播能力；1024/2048 也不代表真实硬件支持的窗口。

## 验证与交付

- 六个正式单元全部 PASS；428 次小型、故障、负例及旧版回归运行和模型/观察器单元检查通过。两组新鲜 512 基线精确复现已验收结果。
- 完整 Payload、逐目标 WQE/TA、SSN/窗口、TP/Jetty 排空、CBFC 和观察器约束保留。没有为得到更快结果关闭检查。
- 每次执行保留 6 GiB RSS、7 GiB 地址空间、每个实验单元 4800 s 宿主机时限及磁盘/主机内存保护。实际串行运行，成功单元峰值 RSS 为 3.596–3.757 GiB；CPU 与 Wall Time 分别记录。
- 最后一组首次执行因执行会话中断没有完整结果，原因未知，不宣称是资源保护或仿真错误。保留现场并核验五组既有结果后，仅在新目录以相同输入、二进制及保护补跑一次。七次尝试对应六个实验单元；残缺输出不进入性能分析。
- 不发布受限真实路由 Trace、逐 Token 数据、原始 Payload 或完整逐包环形日志。公开数据采用有界聚合和选定事件证据。
